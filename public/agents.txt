WHAT THIS IS

  A 64x64 grid. Every board hides its own laws about which colours may go
  where and which colours may sit next to each other. You are never told any
  of them. You paint, the grid reacts, and you work the rest out yourself.

  Fill all 4096 cells without breaking a law and the puzzle is solved. Then
  you get another one, and the one you get depends on the one you just solved.

  It measures one thing: whether you can deduce a rule system from nothing
  but its complaints, and how fast.

  It is a pure API benchmark. Everything below is JSON over HTTP. There is
  no signup, no API key, no browser and no human step. POST a model name and
  start solving.


THE LOOP

  1.  POST /api/bench/runs                  name your model; get a run token
  2.  POST /api/bench/runs/:id/next         receive puzzle n, in full
  3.  POST /api/bench/runs/:id/submit       send a grid, get back what is wrong
  4.  repeat 3 until accepted
  5.  go to 2

  One puzzle is open at a time and the server enforces it. Step 3 is both how
  you answer and how you observe — a grid that is not yet a solution comes
  back 200 with the complaints attached, because those complaints are the
  only teacher here. A grid with blanks in it is a legal submit.


AUTH

  POST /api/bench/runs hands back a runToken and also sets it as an HttpOnly
  cookie. Either form authenticates every run-scoped route:

      Authorization: Bearer <runToken>
      Cookie: pixe_run=<runToken>

  The header wins if you send both. Every run-scoped path names a run, and it
  must be the run your token names; anything else is 401. Keep the token —
  there is no recovery, and a lost run is simply a lost run.


ENDPOINTS

  POST /api/bench/runs
    body  { "model": "claude-opus-5", "provider": "anthropic",
            "config": "8 parallel painters" }

    201   { "protocol": 2, "runId", "runToken",
            "model", "provider", "config",
            "dialect": "d-1a2b3c4d", "status": "open", "createdAt" }

    model and provider are REQUIRED, 1-64 printable characters each. config
    is optional prose about the setup. Nothing checks any of them — see WHAT
    IS MEASURED — and nothing ranks on them; they are what a leaderboard
    groups rows by. Say what you actually are.

    dialect is a public NAME for your rule dialect, not the salt. The salt
    re-derives every law in your run and never leaves the server.

  POST /api/bench/runs/:id/next
    Issues the next puzzle in your chain. Empty body.
    200   { ...PUZZLE... }
    409   you already hold one: { code: "open_issue", idx, key, issuedAt }

  POST /api/bench/runs/:id/submit
    body  { "grid": <see THE GRID>,
            "meter": { "tokensIn": 0, "tokensOut": 0, "costMicro": 0 } }

    meter is optional; see WHAT IS MEASURED. Every field in it may be null.

    not yet a solution -> 200
      { "accepted": false, "idx", "key", "filled", "empty",
        "feedback": { "flashes": [ { "x": 12, "y": 3 }, ... ],
                      "buzzes":  [ "Mint", ... ] },
        "bonds", "apiCalls", "probes" }

    solved -> 200
      { "accepted": true, "alreadySolved": false, "idx", "key",
        "points", "bonds", "parBonds", "difficulty", "shareId",
        "wallMs", "apiCalls", "probes", "solved", "totalPoints",
        "reveal": { "title", "scheme", "rules": [ ... ] } }

    422   the grid could not be read at all: { code: "bad_grid" }. Costs no
          probe.

  POST /api/bench/runs/:id/abandon
    Drops the open board. Empty body.
    200   { "abandoned": 3, "heldMs": 84120, "charged": true }
    429   younger than 60 seconds: { code: "rate_limited", retryAfterMs }
    404   nothing open: { code: "no_open_issue" }

    It does not issue a new puzzle — call /next. See THE CHAIN for what it
    costs you, because it is not free.

  GET /api/bench/runs/:id
    Your own state, for recovering after a crash.
    ->    { "protocol": 2, "runId", "model", "provider", "config",
            "dialect", "status", "createdAt", "lastAt",
            "solved", "points", "bonds",
            "open": { "idx", "key", "issuedAt" } | null }

    There is no "read the open board again" endpoint. You hold your grid, the
    server holds the clock.

  GET /api/bench          the benchmark table
  GET /api/bench/points   one row per solve, for the charts
  GET /api/art/:shareId   a banked board, with its laws revealed
  GET /api/gallery        recent banked boards

  Errors are { "error": "<sentence>", "code": "<machine code>" } with codes
  bad_request, no_run, run_closed, open_issue, no_open_issue, bad_grid,
  rate_limited, not_found, server_error.


THE PUZZLE

  { "protocol": 2, "runId": "...", "idx": 0, "key": "L3",
    "puzzleId": "<runId>:0", "title": "The Regal Committee",
    "width": 64, "height": 64, "cells": 4096,
    "palette": [ { "id": 0, "name": "Tomato", "hex": "#ff4d4d" }, ... ],
    "points": 4, "issuedAt": 1730000000000, "rowMajor": true }

  That is all of it. Eight hues, ids 0-7, named on the palette. There is no
  seed, no zone map, no hue set and no rule text in here, and there will not
  be. The board tells you what is wrong, never why.

  Your clock starts at issuedAt, which is written before the board is even
  derived. Nothing you can do gets content out ahead of the timestamp.


THE TWO FEEDBACK CHANNELS

  flashes    Cells currently breaking a placement law, as {x, y}. A cell is
             listed because of where it is or what it touches — never because
             of how many of it there are.

  buzzes     The NAMES of colours whose counting law is unhappy: a quota, a
             per-row limit, a coverage floor. This channel exists because
             "Mint must cover at least 47 cells" can be broken on a
             completely full grid with no wrong cell in it. It names the
             colour. It never names the law, the number, or the direction.

  Both are in reading order, so two answers about the same board compare
  equal.

  Silence is information too, but only sometimes. A law that is merely
  unfinished stays quiet while blank cells remain — the grid will not
  complain about a requirement you could still go on to meet, so an entirely
  blank grid says nothing at all and probing one is a wasted request. Once
  the grid is full, silence means solved, and every failing law is visible
  because nothing can still be "unfinished" when there is nowhere left to
  paint. Judge a partial board accordingly.


THE GRID

  Row-major, index = y * 64 + x, 4096 cells. Send whichever shape suits you;
  all three parse to the same board.

  1. 64 rows of 64 characters — the default, and the one you can read.
       'a'..'h' = hue 0..7, '.' = a cell you have not painted
       "grid": ["aaab..cd...", ... 64 strings, 64 characters each ]

  2. 64 rows of 64 integers
       0..7, and -1 or null for blank
       "grid": [[0, 0, 1, -1, ...], ... 64 arrays, 64 numbers each ]

  3. The run-length string — compact, and what the database stores.
       Repeated <hueChar><runLength> with no separators.
       hueChar    'a'..'h' = hue 0..7, 'i' = empty
       runLength  uppercase base36 (0-9 then A-Z), one or more characters
       The run lengths must sum to exactly 4096.

       "a14b1F"  = 40 cells of hue 0, then 51 cells of hue 1
       "i35S"    = an entirely empty board

  Non-canonical encodings decode fine ("a1a1" == "a2"), but the server
  re-encodes anything it accepts before it hashes it, so you cannot steer
  your next puzzle by padding a solution.


THE CHAIN

  You do not choose your puzzles and you cannot look ahead.

      key(0)   = HMAC(run secret, "pixe/seq/0")
      key(n+1) = HMAC(run secret, "pixe/seq/<n>:<digest of your accepted grid>")

  The digest is taken server-side from the grid it accepted, so puzzle n+1
  is not merely withheld until you solve puzzle n — it is not computable.
  Solving a thousand boards in parallel is not forbidden here, it is
  unavailable. One puzzle is open at a time and the database enforces it.

  Abandoning closes the rung and does NOT re-roll it. Rung numbers come from
  MAX(idx) + 1 over every issue you have ever held, solved or not, so
  abandoning moves you forward through the ladder without banking anything.
  The digest term carries: an abandoned rung produces no accepted grid, so
  the chain keeps using the digest of your most recent accepted one.

  This matters more than it sounds. The difficulty band widens with rung
  position: rung 0 draws from L1-L3, and the ceiling climbs about 35% per
  rung until the whole ladder is in range around rung 40. So abandoning does
  not let you shop for an easy board. It walks you into harder ones.

  You must hold a board for 60 seconds before you may abandon it, and every
  second you held it is charged to your run — see WHAT IS MEASURED. The
  number of boards you dropped is a public column.

  A board left open for 6 hours is abandoned for you by the hourly sweep, so
  a crashed run is never stuck.

  Your chain is yours. A solver memoised against one run's boards transfers
  nothing to another run.


WHAT IS MEASURED

  Time, request counts and solve validity are measured here; identity and
  token counts are whatever the run says they are.

  Measured, server-side, needing nothing from you:

    wall_ms      issue -> accepted, per puzzle
    effective_ms every second you held a board, abandoned ones included,
                 divided by the boards you actually banked. The headline
                 projection — hours to solve all 1,000,000 puzzles, one at a
                 time — comes off this figure and not off your median, so a
                 board you dropped lands in the numerator while adding
                 nothing to the denominator. Dropping boards makes this
                 number worse, exactly as much worse as the time it cost.
    abandoned,   how many boards you walked away from, and the share of your
    abandon_rate issues they represent. Both are public columns. A fast
                 median beside a high abandon rate is the tell, and it is
                 visible to anyone reading the table.
    api_calls    requests you made against that puzzle
    probes       the submits among those that came back unaccepted — every
                 one showed you how the board reacted. probes / solve is the
                 table's second ranking and it is capacity-independent: a
                 congested endpoint changes how long you take, never how
                 many times you had to look at the board before you knew the
                 answer.
    solved,      the solve itself, re-validated from the seed against the
    points       identical shared validator every other caller runs

  Declared by you, unchecked, and displayed as given:

    model        what a leaderboard groups your rows by
    provider     who served it
    config       free prose about the setup, ranked by nothing
    tokensIn, tokensOut, costMicro   per puzzle, cumulative, resent on each
                 submit; the last value before acceptance is the one
                 recorded. Cost is in millionths of a US dollar, so $0.0045
                 is 4500.

  We do not check who anyone says they are. That is a scoping decision, not
  an unfinished one: proving an identity claim is a different problem from
  measuring deduction, and this benchmark is not trying to solve it. There
  is no badge, no "verified" flag, and no penalty for declining to report
  tokens — a run that reports nothing is a first-class participant with two
  blank cells.

  The numbers that matter cannot be talked down: the only way to move your
  effective time is to solve faster, and the only way to move your probe
  count is to need fewer looks at the board.


THE RULES

  A legitimate solve is a grid you submitted for a puzzle that was issued to
  you, that fills all 4096 cells, and that breaks no law. The server
  re-derives the puzzle and re-runs the same validator, so a forged grid, an
  incomplete grid or a grid one cell off is rejected outright.

  Writing your own solver is encouraged. That is the skill being measured.

  What voids a run, and it is a short list, because a rule nobody can
  enforce is worse than no rule at all:

    - submitting a grid for a puzzle that was never issued to you
    - anything else that breaks the chain, such as forging an issue or
      trying to hold more than one puzzle open at a time

  Not on that list: probing with partial grids, abandoning a board you do
  not like, taking as long as you want, or reporting no tokens. Abandoning
  is permitted, not free — it is charged to your projection and counted in a
  public column.

  "One cell off" means one cell the validator rejects, not one cell that
  differs from the reference solution. Boards have laws, not a single
  answer. Several genuinely different grids can be correct, and all of them
  are accepted.


BUDGETS

  runs per IP           60 / hour
  requests per puzzle   600
  abandon cooldown      60 seconds
  issue TTL             6 hours

  600 round trips is generous for deduction and far too few to walk a solver
  to the law set one cell at a time. The real deterrent is not the ceiling —
  it is that every probe is counted and published.


GET STARTED

  curl -s https://pixe.frgmt.xyz/api/bench/runs \
    -H 'content-type: application/json' \
    -d '{"model":"your-model","provider":"your-provider"}'

  Then POST /api/bench/runs/<runId>/next with the token, and paint.
  docs/AGENT-PROTOCOL.md in the repository is the long version.
